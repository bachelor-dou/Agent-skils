### 项目定位与用途

pdf-inspector 是 firecrawl 旗下的一个快速 Rust PDF 处理库，核心定位是对 PDF 进行分类、文本提取和转 Markdown，并能智能判断文档是文本型、扫描型、图片型还是混合型。它强调在本地完成解析，不依赖 OCR 或外部服务，并提供 Python、Node.js 和浏览器 WebAssembly 绑定，便于在多种运行环境中使用。

### 解决的问题

该项目主要解决 PDF 自动处理中的“是否需要 OCR”和“如何高效提取可用文本”两个痛点。它通过快速采样内容流来识别不同 PDF 类型，并返回置信度与按页路由信息，帮助调用方把扫描件送去 OCR，把文本型 PDF 直接走本地抽取，从而减少不必要的计算开销与外部服务成本。README 还提到它面向约 54% 不需要 OCR 的 PDF。

### 使用场景

适用于需要批量处理 PDF 的检索、解析、归档和文档转换场景，尤其是希望在本地快速完成前置分流与文本抽取的系统。典型用户包括需要做 OCR 路由决策的服务端应用、在 Python 或 Node.js 中集成 PDF 解析能力的开发者，以及希望在浏览器或 Web Worker 中离线处理 PDF 的前端场景。README 中还提到它可输出更适合后续处理的 Markdown。

### 技术架构与特性

项目以纯 Rust 实现，PDF 解析依赖单一库 lopdf，强调轻量和无模型依赖。它支持一次加载文档并复用到检测与抽取流程，减少重复 I/O；支持带位置信息的文本抽取、自动多栏阅读顺序、RTL 文本、CID 字体与 ToUnicode CMap 解码；还支持标题、列表、代码块、表格和页分隔的 Markdown 转换。README 与近期提交记录显示，它也在持续完善表格、布局、密码保护 PDF 和绑定类型同步等能力。

### 项目定位与用途

Cloudflare Computer 是一个运行在 Durable Object 里的虚拟文件系统与执行环境。它把工作区的权威状态保存在 SQLite 中，并通过 `workspace.runtime` 提供可插拔的执行面，支持把同一份工作区接到不同后端上运行。当前已提供容器、Isolate shell 和 Isolate JavaScript 三种后端，分别面向真实 Linux 容器、Shell 执行和 ECMAScript 模块执行。

### 解决的问题

这个项目主要解决工作区状态、文件系统与代码执行分散在不同环境中导致的一致性和切换成本问题。README 说明 Durable Object 持有唯一权威状态，部分后端直接通过 Workers RPC 访问，不需要第二份存储或额外同步；容器后端则把 SQLite 状态投影成真实 FUSE 挂载并回写。它适合在同一抽象下统一处理文件、命令和脚本执行，但信息显示仍处于预览阶段，设计和 API 都可能变化。

### 使用场景

从示例看，它可用于构建带有 `read`、`write`、`exec` 接口的工作区服务，也可作为容器内运行 `computerd` 并通过 HTTP 暴露文件与命令能力的底座。`examples/worker-shell` 和 `examples/worker-javascript` 分别展示了在 Dynamic Worker 中运行 Shell 或 JavaScript 的方式，`examples/think` 则说明它还能作为聊天代理的工作目录。目标用户更偏向实验、探索和原型开发者。

### 技术架构与特性

核心架构是 Durable Object + SQLite 作为权威状态层，外层通过 `workspace.runtime.exec(source, { backend })` 统一入口选择后端执行。容器后端使用 FUSE、`computerd` 和 capnweb RPC，同步工作区状态；Isolate shell 基于 just-bash，在 Dynamic Worker 中通过 Workers RPC 访问工作区；Isolate JavaScript 则支持结构化输入输出、相对导入、配置库、`node:fs/promises` 以及 `ws:git`、`ws:artifacts` 模块。后端按需懒连接，且可按稳定 ID 注册多个后端。

### 项目定位与用途

TurboFieldfare 是一个面向 Apple Silicon Mac 的本地大模型推理项目，核心目标是在约 2 GB 内存预算下运行 Gemma 4 26B-A4B。它提供自定义的 Swift + Metal 运行时，并配套流式安装器、命令行工具和原生 Mac 应用，帮助用户在较低内存设备上完成模型下载、加载与文本生成。

### 解决的问题

该项目主要解决“大模型太占内存、普通 Mac 难以本地运行”的问题。README 明确提到它不会一次性把完整 14.3 GB 模型装入内存，而是保留共享核心与 FP16 KV cache，再按 token 从 SSD 流式读取所需专家，从而让 8 GB RAM 的 Mac 也有机会运行该模型。信息显示它还关注下载、缓存与推理效率。

### 使用场景

典型场景是本地离线或低依赖的大模型文本生成，适合希望在 Mac 上直接体验 Gemma 4 26B-A4B 的开发者、研究者或高级用户。README 中还提到提供本地服务器，并新增了 OpenAI 兼容本地服务和 tool calling，因此也适合需要把本地推理接入其他应用、脚本或工具链的场景。

### 技术架构与特性

项目采用 Swift 6.2 与 Metal 4 实现，运行于 macOS 26+，并且是模型特定实现，不是 MLX 或 llama.cpp 的简单封装。其特点包括流式加载专家权重、共享核心与 KV cache 常驻内存、支持可恢复的精简模型下载，以及前台 Mac App 与 decode-service 的协同运行。README 还提到有 103 条实验记录，覆盖 kernel、缓存、I/O、prefill 和 decode 优化。

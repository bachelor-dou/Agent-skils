# hot-project 服务端底座重构 · 设计

日期:2026-07-30
状态:待评审

## 背景与动机

现有系统 `hot_projects/`(约 10744 行非测试代码)最近完成了数据底座的根本性改造:
放弃了依赖 GitHub stargazers 时间戳 API 实时计算 star 增长的老办法(该 API 自
2026-06-30 起对他人仓库失效),改为每天给 DB 中全部仓库拍一份 star 快照(GraphQL 批量,
存为按天 gz 文件),增长 = 两份快照相减。

底座换了,但上层代码还长在旧底座的残骸上,产生了严重的模块耦合。摸底发现的核心问题:

- **token 池**:对外暴露 token 索引 + 一组手动 `mark_*` 动作,四处调用方各写一遍借还与
  异常标记逻辑,导致 401 处理出现五处、四种口径,其中两处会因一次瞬时 401 把有效 token
  永久烧掉(每日快照跑在 Actions 共享 IP 上,最容易撞瞬时 401,却恰好用了会永久失效的那种)。
- **并发机制**:同时存在四套(dispatcher 协程池、快照采集的手搓 Semaphore+gather、
  describe 的 ThreadPoolExecutor、api 层调用循环轮换),彼此不一致。
- **数据层**:`db.py` 四个写函数各抄一遍"锁→读→改→原子写",约 25 行 × 4,且读盘失败
  处理已漂移(一个返回 0、一个返回 []、`save_db` 却当空字典继续写 —— 会用部分数据覆盖整库)。
- **配置**:`config.py` 反向 import 实现模块(`normalize_models`)、import 时有磁盘副作用
  (`os.makedirs`)、混入 186 行数据资产(`SEARCH_KEYWORDS`)。
- **一次运行多个事件循环**:`main()` 里 `asyncio.run` 与发现阶段内部的 dispatcher 各起一个,
  串行销毁,`token_pool` 被迫写"跨事件循环复用"防御代码。

## 目标与非目标

### 本轮目标(第一轮)

在**新包 `hot_project/`** 中重写服务端底座的四个模块:

1. **配置模块** —— 按生命周期/信任级别切分,清除反向依赖与导入副作用。
2. **数据层** —— 单一事务写原语 + 显式字段归属;快照读写收紧。
3. **token 池** —— 租约式借还,worker 唯一消费者,401/限流单一口径。
4. **任务池** —— 队列 + 协程 worker 持续领取 + 按任务类型限流 + 任务可派生任务。
   本轮建其核心,快照脚本是第一个消费者。
5. **每日快照 CI 脚本** —— 上述四者的第一个端到端消费者,重写并验证跑通。

旧 `hot_projects/` 原封不动继续跑 CI:每日快照链一天都不能断(**快照漏一天永久补不回**,
GitHub 不提供历史 star)。新老共存,新系统读同一份真实数据与旧系统对照验证一致后,再切 CI。

### 非目标(后续轮次)

- 把现有老 Task 子类(采集/增长流水线、Agent+工具层)迁移到新任务池 —— 本轮只建任务池
  核心并让快照脚本用起来;采集/增长流水线、Agent+工具层、Web 层的重写不在本轮。
- 存储格式迁移(SQLite 等)。本轮保持 JSON DB + gz 快照。
- git 体积增长问题(每日 gz 净增、DB 每周全量改写)—— 记录在案,留到格式迁移轮。
- DB 单条记录 9 个字段的精简(98.5% 的 `desc` 为空串却占 key)—— 用户已决定本轮不动。

## 关键约束(已查证,贯穿所有模块)

1. **快照 ⊆ DB**:采集列表就是 `sorted(load_db()["projects"])`。不在 DB 里的仓库不会出现在
   任何快照里;要观测一个新仓库,只能先入库再等一个窗口攒基线,无法追溯历史 star。
2. **快照缺键永不读作 0**:读取 API 只返回 `int | None`,不提供带默认值的取法。缺键读作 0
   会凭空造出等于当前全部 star 的假增长,排到榜首且无人怀疑。
3. **增长相减两端都取自快照**:不混实时值(消除半天偏移,也让"一端快照一端实时"的
   隐性混用在结构上不可能)。
4. **全进程一个事件循环**:消除跨事件循环防御代码。
5. **Python 包导入名用 `hot_project`(下划线)**,分发名可叫 `hot-project`。

## 模块设计

### 1. 配置模块 `hot_project/config/`

按生命周期和信任级别切分,而非按主题堆叠:

| 分类 | 内容 | 规则 |
|---|---|---|
| secrets | `GITHUB_TOKENS`、`LLM_*_KEY`、`SERVERCHAN_SENDKEY` | 只从环境变量读,永不落文件 |
| policy | `MIN_STAR`、`STAR_GROWTH_THRESHOLD`、窗口天数、爆发加成参数 | 可调旋钮,带类型标注 |
| data asset | `SEARCH_KEYWORDS`(现 186 行) | 挪出为独立数据文件,不混在配置里 |
| paths | `DATA_DIR`、`DB_FILE_PATH`、`SNAPSHOT_DIR` 等 | 纯派生,无副作用 |

要修掉的具体问题:

- **反向依赖**:`config.py:153 from .infra.llm_client import normalize_models` —— 配置模块
  反过来 import 实现模块。清洗时掉转方向(归一化逻辑的调用点上移,配置只做声明)。
- **导入副作用**:`config.py:236 os.makedirs(DATA_DIR, ...)` —— 光 import 就建目录,
  测试无法干净导入。目录创建移到真正写入前的运行时。
- **删除**:`CHECKPOINT_FILE_PATH`、`DB_EVICT_GRACE_DAYS`、`DB_EVICT_PROTECT_NEW_DAYS`
  (淘汰规则简化后不再需要)。
- **归属**:CORS 白名单、IP 黑名单属 Web 层配置,不放全局配置(本轮可暂留原处,
  标注归属,Web 层重写时迁走)。

### 2. 数据层 `hot_project/store/`

三个文件:

**`atomic.py` —— 唯一写原语**

```python
@contextmanager
def transaction(path, *, create_if_missing=False) -> Iterator[dict]:
    """独占锁 → 读盘最新版 → yield dict 供修改 → 原子写回(.tmp + os.replace)。
    读盘失败一律抛异常,绝不当空字典继续写(那会用部分数据覆盖整库)。
    调用方抛异常 = 放弃本次写入,盘上保持原样。
    """
```

四个写函数收敛为"在事务里声明改哪些键"的短逻辑,损坏处理只有一份、不可能再漂移。

**`universe.py` —— DB(仓库宇宙)读写**,字段归属唯一声明处:

| 字段 | 谁能写 | 语义 |
|---|---|---|
| `star`, `created_at` | 发现任务(仅新增)、周报刷新 | 观测事实 |
| `desc`, `desc_updated_at` | 报告生成 | LLM 产出,删了不可再生 |
| `gh_desc`, `language`, `topics`, `readme_url` | 周报刷新(仅补空) | 展示字段 |
| `forks` | 周报刷新(**仅当传了 `forks_count`**) | 见下 |

`forks` 的例外必须显式写进归属表:曾发生真事故 —— 候选池改读快照后 `repo_item` 不再带
`forks_count`,而旧 `update_db_project` 无条件覆写 `forks`,把全库 fork 数抹成 0。

保留的两条行为(理由已从"保护 refreshed_at 判据"变为字段归属的自然结果):

- 发现任务只插新键、不合并已有条目 —— 它只带 `star`+`created_at`,合并会用更少字段
  覆盖周报刷出来的展示字段。
- 淘汰不碰顶层 `date` —— `date` 语义是"上次全量刷新",每天改会让它恒为今天、失去意义。

**`snapshots.py` —— 快照读写**,基本沿用现有 145 行(已是干净的单一职责 + 原子写 +
拒绝写空快照),两处改动:

- 文件格式从 `{仓库: star}` 改为 `{"meta": {...}, "stars": {仓库: star}}`。meta 记录:
  - `coverage`:本份快照覆盖率(供锚点选取在容差内优先选覆盖率高的)。
  - `not_found`:本次被 GitHub 判定 null(改名/删库/转私有)的仓库名单,供淘汰使用。
    这个数据现在已在 `main()` 算出并打进日志(`missing = names - stars - failed`),
    落盘时被丢弃;现在写下来,不发任何额外请求。
- "容差顺延"与"自适应短窗口"拆成两个函数:
  - 容差(`SNAPSHOT_ANCHOR_TOLERANCE_DAYS=2`):已攒够快照时,目标 T−N 漏采就顺延 ±2 天。
  - 自适应:还没攒够时,用现存最老快照并报告实际跨度(`Anchor.window_days`)。
  混在一个函数会出现"容差 2 天"与"总共只有 3 天"打架。
- 读取只返回 `int | None`,不留 `.get(name, 0)` 口子(约束 2)。

**删除**:`is_project_window_match`、`timestamp_age_days`、`get_db_age_days` 三个函数,
`DB_DIFF_TOLERANCE_HOURS`/`DB_DIFF_SCALE_MIN_RATIO`/`DB_DIFF_SCALE_MAX_RATIO` 三个常量,
checkpoint 三个函数(`_load/_save/_remove_checkpoint`)。`refreshed_at` 字段保留但降级为
纯运维信息,不再是增长判据。

### 3. token 池 `hot_project/tokens/`

- **租约式借还**:`async with pool.lease() as lease:`,退出作用域自动归还;异常按类型
  自动标记(限流→冷却、401→strikes)。调用方不再接触 token 索引,租约直接提供请求头。
- **唯一消费者**:任务池 worker。全项目所有 GitHub 请求都是任务(CI 与本地 Agent 进程
  隔离,交互式请求不会堵在批量任务后,无需优先级机制)。
- **401 单一口径**:strikes 冷却(连续 N 次才永久失效),消除现有五处四种、其中两处
  会永久烧 token 的 bug。
- **删除**:按索引取头接口(`get_rest_headers(token_idx)`)、跨事件循环防御、
  上一轮加的调用层 `_with_token_rotation`(轮换回到池内部一处)。

### 4. 任务池 `hot_project/tasks/`

单层设计:一个全局池,内部一条队列 + N 个协程 worker 持续领取执行。外部只有 `submit`
一个入口;有真依赖的任务由外部按屏障分批提交(池本身不理解阶段)。

- **任务基类**携带控制属性,可扩展:`needs_github_token`(是否要 token)、
  `max_concurrency`(该类型的并发上限)。以后新增控制维度只加属性。
  只保留一个异步执行入口(现有 `execute`/`execute_async` 双入口中同步版是死代码)。
  去掉 `_token_mgr` 字段:任务只被动接收 worker 递来的 token 租约,不持有池引用
  (现有双通道接触 token 正是双重记账的根源)。
- **按类型限流**:池内维护"任务类型 → 信号量"表。worker 数是总上限,每类任务再受自己
  的 `max_concurrency` 约束(快照批 4、关键词搜索 12)。一个扁平 worker 数表达不了这两种。
- **任务可派生任务**:允许执行中的任务向同一队列提交新任务(星段扫描要先探测 total_count
  才知道切哪些段;GraphQL 批"全 null"退化要对半拆;失败页要重排)。"全部完成"判定须
  正确处理派生(不能在父任务完成时误判队列空)。
- **token 唯一消费者**:worker 领任务时从 token 池取租约递给任务;任务自己不碰池。

### 5. 每日快照 CI 脚本 `hot_project/jobs/daily_snapshot.py`(暂定名)

上述四模块的第一个端到端消费者。七个顶层步骤,其中**三道真屏障**(需外部按顺序编排;
三个收集子阶段之间不是屏障):

1. 幂等检查(当天已有快照则退出)
2. 发现:三阶段收集 star ≥ MIN_STAR 的仓库,新仓库入库 → **屏障:新仓库须先入库**
3. 读 DB 全量仓库名
4. 采集:约 526 个 GraphQL 批,并发上限 4(实测 8 会撞二级限流) → **屏障:须全部完成才能算覆盖率**
5. 覆盖率闸门(< 下限拒绝落盘)
6. 写快照(含 meta:coverage + not_found) → **屏障:淘汰要读含今天在内的最近快照**
7. 淘汰

三个收集子阶段(关键词/星段/Trending)之间**无依赖**:`seen_repos` 只做事后过滤、不省请求,
可一次性并发提交,最后按 full_name 合并去重。

失败策略(各步不同,须显式声明):发现失败→记录并继续(每天自愈);覆盖率不足→中止不落盘;
限流/网络失败→重试,不进淘汰判定。

## 增长口径(本轮定死,实现在后续轮)

- 增长 = 两份快照(T 与 T−N)中同一仓库 star 相减,**两端都取自快照**。
- 创建日期在窗口内(有尾无头)→ 当前 star 即全部窗口增长。
- 仓库不在锚点快照里 → 一律判**未决**,不编数字(三种缺席原因在数据上不可区分)。
- 过渡期(快照未攒够 N 天):窗口自适应到现存最长可用跨度,报告标注实际天数;
  今天仅 1 份 → 无增长可算,次日起 1 天,第 7 天起完整。无需空报告、无需过渡期临时代码。

## 淘汰规则(简化后)

1. 被 GitHub 判 null(改名/删库/转私有)→ 当次淘汰(转私有即便仓库活着我们也永远拿不到)。
2. star < MIN_STAR → 当次淘汰。
3. 限流/网络失败 → 重试,不进淘汰判定(整批失败 ≠ 单仓库 null;须用 meta.not_found
   区分"GitHub 确认查不到"与"我们没问到")。
4. 无迟滞、无连续 N 份、无 desc/收藏/新建保护:误删靠"范围大 + 每天重新发现"自愈;
   desc 是入选才生成的、量极小,重生成可接受(用户决定)。

`evict_stale_projects` 因此瘦成纯函数:给一份快照 + 一份 not_found 名单 → 返回该删的名字。

## 验收方式

本轮无完整端到端产出(增长流水线不在本轮),验收分两层:

1. **对照验证**:新数据层/token 池读同一份真实 DB 与快照,断言读出内容与旧代码逐条相同。
   做成可重复运行的对照脚本,非一次性。
2. **字段归属拦截**:在临时目录上跑写入,断言归属规则真的拦得住越权写(如发现任务试图
   写展示字段或顶层 date、周报刷新在缺 forks_count 时试图把 forks 覆写为 0)。
3. **快照脚本**:用 `--limit` 调试模式对少量仓库跑通全链(发现→采集→写→淘汰),
   与旧脚本输出的快照逐键比对。

## 风险

- **快照断链**:重写期间旧 CI 必须持续跑。切换新脚本上 CI 前,须先本地用真实 token 跑通
  并与旧脚本产出的快照逐键比对一致。
- **误删自愈依赖发现阶段**:淘汰无迟滞的前提是"次日必被重新发现"。若发现阶段长期失败,
  误删不会自愈 —— 但发现失败本身会记录告警,且 star≥MIN_STAR 的仓库被 Search 扫到是高概率事件。
- **meta 格式变更**:快照文件格式从扁平 dict 变为含 meta 的结构。旧快照(扁平)需兼容读取
  (读取层判断:有 `stars` 键走新格式,否则整个 dict 即 stars)。

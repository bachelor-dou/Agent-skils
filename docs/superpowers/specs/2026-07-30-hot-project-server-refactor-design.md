# hot-project 服务端重构 · 设计

日期:2026-07-30
状态:待评审(第二版 —— 并入模块边界、任务/token 契约、增长口径的最终决定)

## 背景与动机

现有系统 `hot_projects/`(约 10744 行非测试代码)刚完成数据底座的根本性改造:放弃依赖
GitHub stargazers 时间戳 API 实时计算 star 增长(该 API 自 2026-06-30 起对他人仓库失效),
改为每天给 DB 中全部仓库拍一份 star 快照(GraphQL 批量,按天存 gz),增长 = 两份快照相减。

底座换了,上层仍长在旧底座的残骸上。摸底查证到的核心问题:

- **token 池**:对外暴露 token 索引 + 一组手动 `mark_*` 动作,四处调用方各写一遍借还与异常
  标记,401 处理出现五处、四种口径,其中两处会因一次瞬时 401 把有效 token 永久烧掉
  (每日快照跑在 Actions 共享 IP 上最易撞瞬时 401,却恰好用了永久失效那种)。
- **并发机制**:同时存在四套(dispatcher 协程池、快照采集的手搓 Semaphore+gather、
  describe 的 ThreadPoolExecutor、api 层调用循环轮换),彼此不一致。
- **配速两套实现**:池内有正确的 async `throttle_search`(仅 `api.py:350` 一处在用),
  同时四处散着同步 `time.sleep(SEARCH_REQUEST_INTERVAL)`(`api.py:777`、`core.py:711`、
  `tasks.py:162`、`tasks.py:337`)。
- **数据层**:`db.py` 四个写函数各抄一遍「锁→读→改→原子写」(约 25 行 × 4),读盘失败处理
  已漂移(一个返回 0、一个返回 []、`save_db` 却当空字典继续写 —— 会用部分数据覆盖整库)。
- **上帝模块**:`tools/basic/core.py` 一个文件同时 import 了配置、三个存储、token 池、
  出站 API、LLM、参数校验、任务池 —— 它既是工具实现,又是收集编排,又是任务池创建者,
  又是 DB 写入方。
- **配置**:反向 import 实现模块(`normalize_models`)、import 时有磁盘副作用(`os.makedirs`)、
- **一次运行多个事件循环**:`main()` 与发现阶段内部的 dispatcher 各起一个,串行销毁,
  `token_pool` 被迫写「跨事件循环复用」防御代码。

## 目标与非目标

### 本轮目标

在**新包 `hot_project/`** 中重写服务端底座:配置、数据层、token 池、任务池,
并让每日快照脚本作为第一个端到端消费者跑通。

旧 `hot_projects/` 原封不动继续跑 CI:每日快照链一天都不能断(**漏一天永久补不回**,
GitHub 不提供历史 star)。新老共存,新系统读同一份真实数据与旧系统对照一致后再切 CI。

### 本轮做「适配」而非「重写」的部分

顶层的 `api_server.py`、`agent_cli.py`、其余 `cron_*.py`:**只换接线,业务逻辑照搬。** 它们要从旧的
`db.py`/`token_pool`/`dispatcher` 改成新的 `infra.store`/`tokens`/`infra.tasks`,
接口形状变了(租约取代 token 索引、事务取代四份手抄的锁读改写),但它们做的事不变。

判据:改动应集中在 import 与调用形式;凡是要动业务判断的,说明该逻辑本就属于下层,
应下沉到工具层,而不是在入口脚本里改。

### 非目标(后续轮次)

- 采集/增长流水线的重写、Agent+工具层的重写、Web 层的功能性重写。本轮只建底座 + 快照脚本
  + 上述接线适配。
- 存储格式迁移(SQLite 等)。本轮保持 JSON DB + gz 快照。
- git 体积增长(每日 gz 净增、DB 每周全量改写)。记录在案,留到格式迁移轮。
- DB 单条记录 9 字段精简(98.5% 的 `desc` 为空串却占 key)。用户已决定本轮不动。

## 关键约束(已查证,贯穿所有模块)

1. **快照 ⊆ DB**:采集列表就是 `sorted(load_db()["projects"])`。不在 DB 里的仓库不会出现在
   任何快照里;要观测一个新仓库只能先入库再等一个窗口攒基线,无法追溯历史 star。
2. **快照缺键永不读作 0**:读取 API 只返回 `int | None`,不提供带默认值的取法。缺键读作 0
   会凭空造出等于当前全部 star 的假增长,排到榜首且无人怀疑。
3. **增长相减两端都取自快照**:不混实时值,让「一端快照一端实时」在结构上不可能。
4. **全进程一个事件循环**:消除跨事件循环防御代码。
5. **包导入名 `hot_project`(下划线)**,分发名可叫 `hot-project`。

## 模块边界

两条**互相垂直的轴**。混在一起是当前耦合的成因:`tools/basic/core.py` 是一个纵层横向抓了三个横轴设施、
还兼职编排。

**纵轴 —— 调用栈,上层依赖下层,单向,下层永不 import 上层:**

| 位置 | 职责 | 判据 |
|---|---|---|
| 顶层脚本 `api_server.py` / `cron_*.py` / `agent_cli.py` | 编排入口 | **唯一知道全部接线的地方**,不该解耦。位置与旧包一致 |
| `agent/` | agent 核心:对话、prompt、state | — |
| `tools/` | agent 可执行能力 + 能力清单 | 工具之间**零 import**(现已成立,须守住) |
| `provider/` | 出站:Provider 抽象 + github 实现 | 对包外只暴露 Provider |

**横轴 —— 共享设施,被多个纵层使用,各自单一所有者 + 窄接口:**

| 包 | 内容 |
|---|---|
| `infra/store/` | 数据层:DB 宇宙 + 快照 + 收藏,共用一个事务原语 |
| `infra/tasks/` | 全局任务池 |
| `infra/llm/` | LLM 客户端 + key 管理 |
| `infra/notify.py`、`infra/exceptions.py` | 通知机制、共享异常词汇 |
| `config.py` | 策略旋钮、路径、机密读取、关键词表 |

**纯逻辑 —— 零 I/O,可独立测试:**

| 包 | 内容 | 现状 |
|---|---|---|
| `common/` | 时间(UTC 时钟、时间戳解析、年龄)、环境变量解析 | 旧包每个模块各写一遍 `utc_today()` / `_now()` / `_DATE_FMT` |

**纯算法不单独立层。** 判据是**调用方个数**,不是纯不纯:

- 一个调用方 → 就写在调用方里(淘汰判定在 `cron_daily_snapshot.py`、Trending 解析在
  `provider/github/trending.py`)。为它隔一层买到的边界是零,代价是读一件事要开两个文件。
- 多个工具共用 → 才提上来。第一个够格的是**增长相减**:周报排名、爆发探针、单仓库查询
  要用同一套算法,各写一份迟早算出三个不同的增长值。到那时再建 `core/`(连同「零 I/O」的
  分层守卫一起),不必提前占位 —— 空目录是个不一定兑现的承诺。

### 落地布局(贴着旧包的形状)

```
hot_project/
  api_server.py    HTTP 服务入口(顶层,同旧包)
  agent_cli.py     命令行入口
  cron_*.py        定时任务入口
  web/             前端静态文件(chat.html / report.js,同旧包)
  config.py        旋钮 / 路径 / 机密 / Web 安全 / LLM 目录 / 关键词表
  common/          timeutil, env —— 零项目知识,换个项目能原样拷走
  infra/
    store/         atomic(事务原语), universe(DB), snapshots, favorites
    tasks/         任务池 + 任务基类
    llm/           客户端 + key 管理
    notify.py  exceptions.py
  provider/
    base.py        Provider 协议
    github/        client(出站请求), trending, tokens(池)
  tools/           每个工具一文件,自带 ToolSpec 声明
  agent/
  data/  report/  logs/  tests/
```

与旧包只有一处结构差异:**新增 `common/`** —— 零项目知识的小工具(时间、环境变量)。
它有可执行的成员判据,见下面 1b 节;没有判据的 `common/` 才是杂物间。

(增长/打分等纯算法按上面那条规矩安置:够格提上来时再建 `core/`。)

入口脚本仍在顶层、前端仍在 `web/`,与旧包一致。**没有 `entry/` 这种包** —— 入口放顶层
一眼能看见,再包一层只是多一次目录跳转。

### 数据与产出的归属

数据现在全挂在 `PACKAGE_DIR` 下(`config.py:234-241`),于是「移包」等于「移数据」。
而数据不是代码,不该住在一个计划要删掉的包里面。终态:**数据目录提到仓库顶层,不属于任何包**。

| 资产 | 现位置 | git | 终态 | 过渡期做法 |
|---|---|---|---|---|
| `Github_DB.json` 30MB | `hot_projects/data/` | main 已追踪 | 仓库顶层 `data/` | 新包**只读**旧目录 |
| `favorites.json` | `hot_projects/data/` | main 已追踪 | 顶层 `data/` | 只读 |
| `snapshots/*.json.gz` | `hot_projects/data/snapshots/` | **tmp 分支**追踪 | 顶层 `data/snapshots/` | 只读 |
| `report/*.md` 1.7MB | `hot_projects/report/` | main 已追踪 | 顶层 `report/` | 只读 |
| `logs/` 49MB | `hot_projects/logs/` | 未追踪 | 各包自己写 | 不搬 |
| `.pipeline_checkpoint.json` | `hot_projects/data/` | 已忽略 | **不存在** | 不搬(无 checkpoint) |

**过渡期不复制数据。** 复制的代价不是存储(内容相同时 git 复用同一 blob),而是**权威性**:
旧 CI 每天写旧目录,副本从复制那刻起就停在过去,拿新代码的产出去比一份冻结的副本毫无意义 ——
影子比对的全部价值就没了。所以:

- **读** —— 新包 `paths.py` 指向旧包的真数据目录,与旧 CI 共读同一份唯一权威。
- **写** —— 新包写到独立的影子目录(gitignore),绝不覆盖真快照/真 DB。
- **切换** —— 切 CI 那天数据整体搬到顶层,`paths.py` 改一行。此后删掉 `hot_projects/` 不碰数据。

**为什么不现在就搬到顶层**:那要改旧 `config.py` 的四个路径常量,而旧流水线是唯一不能坏的东西
(快照漏一天永久补不回)。改新包一行(它还没在跑)比改运行中的那个便宜得多。

**过渡期的现实摩擦**:`snapshots/` 只在 tmp 分支上。做影子比对时工作区要能同时看到 tmp 的快照
与 main 的代码,操作步骤在计划里写明。

### 两处必须改的命名

- **「api」在旧代码里有两个相反含义**:`api_server.py` 是**入站**(浏览器 → 我们),
  `provider/github/api.py` 是**出站**(我们 → GitHub)。新名分别为 `api_server.py`(沿用旧名)和
  `provider/github/client.py`。
- **GitHub 出站属 provider 内部,不属工具层内部**。判据:每日快照任务不是工具,却需要
  GitHub 收集;若出站住在 `tools/` 下,批处理脚本就必须 import 工具层 —— 这正是今天的病灶
  (`cron_daily_star_snapshot.py` 现在 `from ...tools.tool.ranking import _collect`)。
  放在 `provider/github/` 下、只经 Provider 对外,tools 与入口脚本就是平级消费方。

### 旧 `tools/basic/core.py` 的解散走向

| 现有内容 | 去向 |
|---|---|
| 收集编排(三阶段调度、建 dispatcher) | 顶层入口脚本 —— 编排是它的职责 |
| 增长计算 | 纯快照相减,本就无需 I/O。三个工具共用,是第一个够格提成 `core/growth.py` 的 |
| 工具实现(search/scan/growth 对外那层) | `tools/` 各自一文件 |
| 参数校验调用 | `tools/` 内部 |

`report.py` 同样拆两半:抓 readme/commits + 调 LLM 是**取证**(有 I/O,归任务);
`dict → markdown` 是**渲染**(纯)。`report_parse.py` 只 import `re`,
已经是渲染的纯逆运算,两半应放在一起。

判定「归 infra 还是归产品逻辑」的唯一判据:**换个产品还能用的是 infra**。文件锁、HTTP 重试、
token 轮换、任务调度换成 npm 包追踪器照样能用;报告渲染知道 star 增长、分类、爆发探针,
它是产品逻辑。把它放进 infra 会让 infra 反向依赖领域知识,循环 import 就是这么来的。

## 模块设计

### 1. 配置 `hot_project/config.py`

**位置与旧包相同 —— 单个顶层文件。**「改行为就打开 config.py」是这个项目里辨识度最高的
约定,不该为了分类整齐把它拆成包(拆完想改一个阈值得先猜它在 policy 还是 paths)。

六节,顺序按「你多久改一次」排 —— 旋钮在第一屏,最长且最少改的关键词表垫在最后
(旧文件里它本来也在最后,252 行往下,并没有埋住旋钮):

| 节 | 内容 | 规则 |
|---|---|---|
| 一 策略旋钮 | `MIN_STAR`、`MAX_STAR`、`STAR_GROWTH_THRESHOLD`、窗口天数、爆发加成 | 放最前,每个注明调大调小的后果 |
| 二 路径 | `READ_*` / `WRITE_*` / `DB_*_PATH` / `SNAPSHOT_*_DIR` | 纯派生,import 期不碰磁盘 |
| 三 机密 | `github_tokens()`、`llm_key()`、`serverchan_sendkey()` | 只从环境变量读,永不落文件 |
| 四 Web 安全 | CORS 白名单、IP 黑名单 | 只有 api_server 一个消费者 |
| 五 LLM 平台目录 | `LLM_MODELS` | 纯声明,只记 `key_env`,不含 key |
| 六 搜索关键词词典 | `SEARCH_KEYWORDS`(186 行) | 位置与旧包一致 |

环境变量的解析口径(`csv_list` / `flag` / `text`)不在这里,归 `common/env.py` ——
它零项目知识,不该住在配置里。

### 1b. 公共小工具 `hot_project/common/`

    timeutil.py   UTC 时钟、GitHub 时间戳与日期串的解析/格式化、年龄计算
    env.py        环境变量解析

它存在是因为有**已经发生的**重复:`favorites` 自己写 `_now()`,`snapshots` 自己写
`utc_today()` 加自己的 `_DATE_FMT`,而增长与淘汰还要判 `created_at` 是否落在窗口内。
一律 UTC —— 混用本地时区会让窗口差一天(快照按 UTC 命名,东八区下午算「今天」会去找
一个还不存在的锚点)。

「common」天生会变成杂物间,因为这个名字没说清什么**不该**进来。所以它的成员判据被写成
可执行的测试(`test_common_knows_nothing_about_the_project`):**零项目知识** —— 标识符和
字面量里出现 star / repo / snapshot / token 这类词就红,换个完全不同的项目每个文件能原样
拷走。光靠「不许 import 上层」挡不住 `def is_hot(stars): return stars > 1000` 这种不需要
import 的项目逻辑,而它正是杂物间的第一块砖。

共用层的判据互不重叠:`common` 零项目知识 /
`infra` 有状态的机制但不懂产品。拿不准就问:这段代码提到 star 了吗?

要修掉的:

- **反向依赖**:`config.py:153 from .infra.llm_client import normalize_models` —— 配置反过来
  import 实现模块。归一化的调用点上移,配置只做声明。
- **导入副作用**:`config.py:236 os.makedirs(DATA_DIR, ...)` —— 光 import 就建目录,测试无法
  干净导入。目录创建移到真正写入前的运行时。
- **删除**:`CHECKPOINT_FILE_PATH`(无 checkpoint)、`DB_EVICT_GRACE_DAYS`、
  `DB_EVICT_PROTECT_NEW_DAYS`(淘汰简化后不需要)、`SEARCH_REQUEST_INTERVAL`(移入 token 池)。
- **归属**:CORS 白名单、IP 黑名单属 Web 层配置,留在 `config.py` 第四节,只有 api_server 一个消费者。

**不该进 config 的**:批大小 100(实测别名上限,200 会静默返回全 null)、快照并发 4
(实测二级限流上限)、锚点容差 2 天、覆盖率下限 0.5。这些是实测定死的实现细节,放旋钮位置
会诱人去调,而调错后果是静默污染基线。它们归各自模块顶部,带注明理由的注释。

### 2. 数据层 `hot_project/infra/store/`

**`atomic.py` —— 唯一写原语**

```python
@contextmanager
def transaction(path, *, create_if_missing=False) -> Iterator[dict]:
    """独占锁 → 读盘最新版 → yield dict 供修改 → 原子写回(.tmp + os.replace)。
    读盘失败一律抛异常,绝不当空字典继续写(那会用部分数据覆盖整库)。
    调用方抛异常 = 放弃本次写入,盘上保持原样。
    """
```

四个写函数收敛为「在事务里声明改哪些键」,损坏处理只有一份、不可能再漂移。

**`universe.py` —— DB 读写**,字段归属唯一声明处:

| 字段 | 谁能写 | 语义 |
|---|---|---|
| `star`, `created_at` | 发现任务(仅新增)、周报刷新 | 观测事实 |
| `desc`, `desc_updated_at` | 报告生成 | LLM 产出 |
| `gh_desc`, `language`, `topics`, `readme_url` | 周报刷新(仅补空) | 展示字段 |
| `forks` | 周报刷新(**仅当传了 `forks_count`**) | 见下 |

`forks` 的例外必须显式写进归属表:曾发生真事故 —— 候选池改读快照后 `repo_item` 不再带
`forks_count`,而旧 `update_db_project` 无条件覆写,把全库 fork 数抹成 0。

保留两条行为(理由从「保护 refreshed_at 判据」变为字段归属的自然结果):

- 发现任务只插新键、不合并已有条目 —— 它只带 `star`+`created_at`,合并会用更少字段覆盖
  周报刷出来的展示字段。
- 淘汰不碰顶层 `date` —— `date` 语义是「上次全量刷新」,每天改会让它恒为今天、失去意义。

**`snapshots.py`** 沿用现有 145 行(已是干净的单一职责 + 原子写 + 拒绝写空快照),三处改动:

- 格式从 `{仓库: star}` 改为 `{"meta": {...}, "stars": {仓库: star}}`。meta 记录:
  - `coverage`:本份覆盖率(供锚点在容差内优先选覆盖率高的)。
  - `not_found`:本次被 GitHub 判 null(改名/删库/转私有)的仓库名单,供淘汰使用。
    这份数据现在已在 `main()` 算出并打进日志(`missing = names - stars - failed`),落盘时
    被丢弃;现在写下来,不发任何额外请求。
  - 兼容读:有 `stars` 键走新格式,否则整个 dict 即 stars。
- 「容差顺延」与「自适应短窗口」拆成两个函数。混在一个会出现「容差 2 天」与「总共只有 3 天」
  打架。
- 读取只返回 `int | None`,不留 `.get(name, 0)` 口子(约束 2)。

**删除**:`is_project_window_match`、`timestamp_age_days`、`get_db_age_days`,
`DB_DIFF_TOLERANCE_HOURS`/`DB_DIFF_SCALE_MIN_RATIO`/`DB_DIFF_SCALE_MAX_RATIO`,
checkpoint 三函数。`refreshed_at` 保留但降级为纯运维信息,不再是增长判据。

### 3. token 池 `hot_project/provider/github/tokens/`

池子对每个 token 管**三件事**,「拿到一个可用 token」= 三者同时满足:

1. **占用** —— 是否已被别人借走
2. **冷却** —— 是否在限流/401 冷却中(`available_at`)
3. **配速** —— 距该 token 上次请求是否已满最小间隔

第 3 条现在只有 async 版被一处调用,其余四处是同步 `time.sleep` 抄写。**配速必须在池内**,
否则会出现今天日志里的现象:并发 = token 数时,12 个请求在 500ms 内打完、烧光每分钟配额,
然后集体撞二级限流(今天 11:00 那轮 143 页失败、3 轮补偿就是这个)。

契约:

- **租约式借还**:`async with pool.lease() as lease:`,退出作用域自动归还;异常按类型自动
  标记(限流→冷却、401→strikes)。调用方不接触 token 索引,租约直接提供请求头。
- **唯一消费者**:任务池 worker。全项目所有 GitHub 请求都是任务(CI 与本地 Agent 进程隔离,
  交互式请求不会堵在批量任务后,无需优先级机制)。
- **401 单一口径**:strikes 冷却(连续 N 次才永久失效),消除现有五处四种、其中两处会永久
  烧 token 的 bug。
- **删除**:按索引取头接口(`get_rest_headers(token_idx)`)、跨事件循环防御、上一轮加的
  调用层 `with_token_rotation`(轮换回到池内部一处)、四处同步 `time.sleep` 配速。

**不与 LLM key 管理共用抽象**:两者形状相同(多把钥匙、轮换、限流、重试),但各约 200 行、
真正共用的只有「挑冷却最早结束的那把」约 40 行,而 GitHub 的 403 语义与各 LLM backend 的
错误码差得很远,强行统一会长出一堆分支。各自实现、形状对齐即可。

### 4. 任务池 `hot_project/infra/tasks/`

一个全局池:一条队列 + N 个协程 worker 持续领取执行。外部只有 `submit` 一个入口;有真依赖的
任务由外部按屏障分批提交(池本身不理解阶段)。

**任务基类携带控制属性,子类给默认值,调用方可覆盖。** 三级解析:调用方显式 → 子类默认 →
基类默认。理由:「快照批并发 4」是关于**任务类型**的实测知识,该跟着类走,要求每个调用点
重复写这个数字迟早会分叉(某处写 8 就静默退化);但环境会变(Actions 共享 IP 比住宅 IP 更
易触发限流),所以必须留覆盖口。

**并发度的三种制度 —— 只有一种需要写数字:**

| 制度 | 声明 | 上限从哪来 | 例子 |
|---|---|---|---|
| token 绑定 | `concurrency = None` + `needs_github_token = True` | **租约本身**:池里有几个可用 token,就最多几个任务能同时持租约 | 关键词搜索、星段扫描页 |
| 速率绑定 | `concurrency = 4` | 写死。二级限流按 IP+请求速率计,**与 token 数无关**,加 token 不管用 | GraphQL 快照批 |
| 无限制 | `concurrency = None` + `needs_github_token = False` | worker 数 | Trending 抓取(纯 HTML,不吃 token)、本地计算 |

关键结论:**token 绑定的任务不需要信号量**。池子本身就是一个容量恒等于「当前可用 token 数」
的信号量 —— 加 token 立刻变宽,token 失效立刻变窄,永远是最新值,零额外代码。所以旧设计里的
`max_concurrency = 12` 不是「要改成动态」,而是**该删掉**:它与租约重复记账,而写死的 12 在
token 增减后就是错的。

唯一保留字面量的是速率绑定,而写死在那里是**正确的**:4 是 IP 级二级限流的实测上限,它不随
token 数变化(实测:并发 3 顺畅;12 token 时用并发 8,整批 token 被限、反复等 60s 重置)。

其余契约:

- 只保留一个异步执行入口(现有 `execute`/`execute_async` 双入口中同步版是死代码)。
- 去掉 `_token_mgr` 字段:任务被动接收 worker 递来的租约,不持有池引用(现有双通道接触
  token 正是双重记账的根源)。
- **任务可派生任务**:允许执行中的任务向同一队列提交新任务(星段扫描要先探 total_count 才
  知道切哪些段;GraphQL 批「全 null」退化要对半拆;失败页要重排)。「全部完成」判定须正确
  处理派生,不能在父任务完成时误判队列空。

### 5. 工具层 `hot_project/tools/`(本轮定死设计,实现在后续轮)

**单点声明**。现在有**两份中心清单要人手对齐**:`schemas.py` 存 14 个 schema、
`registry.py` 存 14 个 handler 映射,靠 `schema_by_name[name]` 对上 —— 加一个工具要改三处,
一旦对不上是启动时 `KeyError`。改为每个工具文件自己声明 `ToolSpec`(name / schema / handler /
expensive),清单只负责收集。加工具 = 只碰一个新文件。

模块名从 `registry` 改为体现职责的名字(它是 agent 能力清单,不是通用注册表)。

**工具之间零 import**(现已成立,须守住)。两类看起来像依赖的东西要分开:

- **实现复用**:榜单工具内部要做 search/scan/trending/describe 的事,而这四件事各自也是独立
  工具。这不是工具依赖工具,是两者都依赖下面那层。规则:共用逻辑一律下沉,不横向 import。
- **数据依赖**:`analyze_report` 要先有报告、`recall_tool_result` 要先有上轮结果、
  `add_favorite` 要先有仓库名。这类顺序由 **agent 在对话里决定**,不写进代码。它们作为代码
  保持独立是对的 —— 依赖活在对话里,不在 import 里。

### 6. 每日快照 `hot_project/cron_daily_snapshot.py`

七个顶层步骤,其中**三道真屏障**:

1. 幂等检查(当天已有快照则退出)
2. 发现:三阶段收集 star ≥ MIN_STAR 的仓库,新仓库入库 → **屏障:新仓库须先入库**
3. 读 DB 全量仓库名
4. 采集:约 526 个 GraphQL 批,并发 4 → **屏障:须全部完成才能算覆盖率**
5. 覆盖率闸门(< 0.5 拒绝落盘)
6. 写快照(含 meta:coverage + not_found) → **屏障:淘汰要读含今天在内的最近快照**
7. 淘汰

三个收集子阶段(关键词/星段/Trending)之间**无依赖**,可一次性并发提交,最后按 full_name
合并去重(`seen_repos` 只做事后过滤、不省请求)。三者资源需求不同,正好对应上面三种并发制度:
关键词与星段页是 token 绑定,Trending 不吃 token 也不受 Search 限流,可完全免费地并行。

**星段拆分改按层并发。** 现状:`auto_split_star_range` 深度优先串行递归,每次请求间隔 1.3s。
今天 11:00 那轮它耗了 **5 分 17 秒**(11:09:26 → 11:14:43,全程零日志)产出 95 个子区间,
期间只用掉 46 次/分钟的容量、12 个 token 有 87% 闲着。而递归的**兄弟节点互不依赖**:探测
`500..1000` 溢出后拆成的 `500..750` 与 `750..1000` 谁先探完全无关。改成按层提交(BFS),
95 个叶子约 7 层,7 轮并发探测替代约 190 次串行请求,这一段能压到一分钟内。

失败策略(各步不同,须显式声明):发现失败→记录并继续(每天自愈);覆盖率不足→中止不落盘;
限流/网络失败→重试,不进淘汰判定。

## 增长口径(本轮定死,实现在后续轮)

**只有两条规则**,其余一律未决:

1. **锚点相减**:T−N 那天快照里有这个仓库 → `当前 star − 锚点 star`。精确。
2. **窗口内新建**:仓库不在锚点快照里,但 `created_at` 在窗口内(有尾无头)→ 当前 star 即
   全部窗口增长。精确。
3. 其余 → **未决**。不是零增长:不进候选池、不写 DB,等快照攒够下一轮自然算出来。

**要删掉的两条旧路**(旧代码 `_resolve_growth_without_timestamps` 的四条中的后两条):

| 旧路 | 算法 | 删除理由 |
|---|---|---|
| DB 差值 | `当前 − DB 旧 star`(要求 `refreshed_at` ≈ 窗口 ±5h) | 每个仓库 `refreshed_at` 各异,不同仓库拿到不同的实际窗口,榜单之间不可比。而锚点法的全部价值正在于「所有仓库共用同一份锚点、窗口长度一致」 |
| DB 折算 | `delta × 窗口 / 快照年龄` | 乘法外推,会凭空造 star。旧代码注释自己也承认是过渡方案 |

**窗口必须用锚点的实际跨度,不是请求值。** 旧代码有个会让榜单少人的 bug:

```python
anchor = _load_growth_anchor(time_window)
if anchor is not None:
    growth_ctx["effective_growth_calc_days"] = anchor.window_days   # 只改了统计口径
...
resolved = _resolve_growth_without_timestamps(
    ..., time_window, anchor_stars,      # ← 判定仍用请求值
)
```

锚点顺延时(请求 7 天、当天缺快照顺延到 T−9),`window_days` 变成 9 只用于报告口径,规则 2
的 `created_at` 比较仍用 7。于是 8 天前创建的仓库:锚点里没有(9 天前不存在)→ 落空;
`8 <= 7` 为假 → 落空 → 记未决被剔出排名。但它本该精确算出:锚点窗口实际 9 天,仓库仅 8 天大,
全部 star 都是这 9 天内涨的。这是**少算**(丢候选),而缺快照顺延的日子正是新仓库最多的日子。
新实现里窗口只有一个来源:锚点的实际跨度。

**过渡期**(快照未攒够 N 天):窗口自适应到现存最长可用跨度,报告标注实际天数。今天仅 1 份 →
无增长可算;次日起 1 天;第 7 天起完整。无需空报告、无需过渡期临时代码。

## 淘汰规则

1. 被 GitHub 判 null(改名/删库/转私有)→ 当次淘汰(转私有即便仓库活着我们也永远拿不到)。
2. `star < MIN_STAR` → 当次淘汰。
3. 限流/网络失败 → 重试,不进淘汰判定(整批失败 ≠ 单仓库 null;须用 `meta.not_found` 区分
   「GitHub 确认查不到」与「我们没问到」)。
4. 无迟滞、无连续 N 份、无 desc/收藏/新建保护:误删靠「范围大 + 每天重新发现」自愈;
   desc 是入选才生成的、量极小,重生成可接受(用户决定)。

淘汰因此瘦成纯函数:给一份快照 + 一份 not_found 名单 → 返回该删的名字。它只有每日快照
一个调用方,所以就写在 `cron_daily_snapshot.py` 里(`decide()`),不单独立层。

## 效率结论(用真实日志核过)

**这个作业是限流绑定的,不是结构绑定的。** 今天 11:00 那轮:全程反复出现
`当前无可用 token，最早 47.01s 后恢复`;10:00 那轮启动 **90 秒**就把 12 个 token 全烧完。
搜索 API 是 30 次/分钟/token,12 个 token 合计 360 次/分钟;333 个关键词 × 最多 10 页 +
95 个区间 × 最多 10 页 ≈ 三四千次请求,除以 360 就是十几分钟的硬地板。**改结构碰不到这个地板。**

所以重构对性能的作用是「填掉本可以发请求却在空转的窗口」,共两处,都已写进设计:

1. **星段拆分的 5 分 17 秒**(见上,按层并发可压到一分钟内)。这是唯一一处大额结构性空转。
2. **配速与冷却集中到池内**,减少「先打出去、吃个 403、再赔 60s 冷却」的无效请求
   (今天 143 页失败、3 轮补偿)。

抽象自身的开销**量级上不可测**:每任务多一次信号量获取 + 一次租约上下文,是微秒级;对面是
几百毫秒的网络请求和 47 秒的限流冷却。526 个快照任务的全部调度开销加起来不到一次请求的往返。
换语言也买不到东西:唯一的 CPU 密集段是 30MB JSON 读写(约 1.2s)和 gzip,都是 C 实现且释放
GIL;真正的计算(增长相减)实测 11.6ms。

**真正的杠杆不在结构,记入后续:**

- **星段拆分结果缓存到明天**。24 小时内 star 分布几乎不变,昨天的 95 个区间今天照用,只重探
  溢出的那些。这比并发化更彻底 —— 直接把整个拆分阶段清零。
- **量化 333 个关键词的边际发现量**。DB 宇宙已 52571 个,关键词搜索新增仓库的边际收益应在
  快速衰减,可用数据支撑砍掉一批。

这两条收益(分钟级)比结构优化还大,且需要干净的数据层才好做,所以放在底座之后。

## 验收方式

本轮无完整端到端产出(增长流水线不在本轮),验收分三层:

1. **对照验证**:新数据层/token 池读同一份真实 DB 与快照,断言读出内容与旧代码逐条相同。
   做成可重复运行的对照脚本,非一次性。
2. **字段归属拦截**:在临时目录上跑写入,断言归属规则真的拦得住越权写(发现任务试图写展示
   字段或顶层 `date`;周报刷新在缺 `forks_count` 时试图把 `forks` 覆写为 0)。
3. **快照脚本**:用 `--limit` 调试模式对少量仓库跑通全链(发现→采集→写→淘汰),与旧脚本
   产出的快照逐键比对。

并发制度的三档各留一个可运行检查:token 绑定的任务在 token 数变化后并发度随之变化;
速率绑定的任务并发恒为 4 且不随 token 数变化;无限制任务不占租约。

## 风险

- **快照断链**:重写期间旧 CI 必须持续跑。切新脚本前须先本地用真实 token 跑通并与旧脚本产出
  的快照逐键比对一致。
  当前状态:07-30 的快照尚未落盘(`data/snapshots/` 只有 `2026-07-29.json.gz`),
  10:00 那轮在 10:01:32 被切断、11:00 那轮重跑。这本身就是「发现阶段太慢导致整轮跑不完」的
  症状,也是本轮要缓解的目标之一。
- **误删自愈依赖发现阶段**:淘汰无迟滞的前提是「次日必被重新发现」。若发现阶段长期失败,
  误删不会自愈 —— 但发现失败本身会告警,且 `star ≥ MIN_STAR` 的仓库被 Search 扫到是高概率事件。
- **meta 格式变更**:快照格式从扁平 dict 变为含 meta 的结构,读取层须兼容旧格式。
- **按层并发拆分改变请求时序**:拆分从串行变并发后,它会与其他发现任务竞争同一份限流额度。
  收益的前提是「那 5 分钟确实有闲置容量」(已核:只用了 46/360 次每分钟)。若实测并非如此,
  退回串行,该项收益作废但不影响正确性。
